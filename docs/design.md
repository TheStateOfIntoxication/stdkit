# stdkit 设计文档

写给两类人：想用这套规范的人，和想知道它为什么长这样的人。尽量不假设你熟悉静态分析、AST 或 Agent 框架——
每个机制都会先说「它解决什么麻烦」，再说「怎么实现」。

想看怎么改代码，去 [开发文档](development.md)。想快速上手，去看 [README](../README.md) 和 [安装说明](install.md)。

---

## 1. 一句话，然后说清楚

**stdkit 是把「团队代码规范」变成可执行、可校验、可分发给 AI 的一份东西。**

再说细一点，它做三件事：

1. **规则只有一份**，写在 Markdown 里，每条有稳定编号（`J8-API-04` 这种）。
2. **能机判的不交给模型**：49 条规则写成了正则，在本机跑完，直接告诉你 `文件:行号`。
3. **判不了的说明白谁判**：剩下 78 条需要看调用链、看语义，明确交给模型（或人），并写清「机器抓不到」。

改规则之后，给 AI 用的四类产物（skill、审查提示词、客户端适配文件、仓级约定）会一起重新生成，不用手抄第二遍。

---

## 2. 问题：规范为什么会烂掉

先说三个很多人都见过的场景。

**场景一，同一个规定有三份，谁也不确定哪份最新。**
wiki 里写「金额必须用 BigDecimal」，`AGENTS.md` 里写「Money 用 BigDecimal」，某次评审评论里说「Float 也能凑合」。
新人问一句「到底按哪个」，回答是「你看最近那个 PR」。规则本身不难，难的是**你没法确认你看到的是不是最新的**。

**场景二，规范写了，但没有东西保证它被遵守。**
「禁止 `double` 存金额」这句话写在文档里。真有人写了 `private double amount;`，能不能拦住？只能靠有人正好看到。
也就是规范是「期望」，不是「约束」。

**场景三，用 AI 的团队会遇到同一个问题，而且还多一层。**
为了让模型按规范写代码，大家开始往仓库里放 `AGENTS.md`、`.cursorrules`、`copilot-instructions.md`、各种 prompt 模板。
这些文件是**手写的副本**。改一条规则，得记得去改四个地方。忘一个，模型就按旧规则给你补代码，而且它不会告诉你它用的是旧的。

这三个场景的共同点：**知识存在多份副本，并且只有人能维护一致性**。人一定会忘。

stdkit 的判断是：这件事该交给机器。

## 3. 核心思路：一份事实源 + 生成 + 分层判定

三个原则，一句话一个：

**原则一：规则只写一遍，其余全部生成。**
`rules/` 目录是唯一事实源。`catalog/rules.json`（机器索引）、`dist/`（给各客户端的产物）都由命令生成。
生成物提交进仓库，但不许手改——`ds check` 会比对，改了不重建就报错。

**原则二：判定按「判据在哪」分层，各层只做自己能做的那部分。**
看单行文本就能下结论的，用正则，零成本；要看多个文件才能判的，用仓级检查；要看调用链的，交给模型；
规范本身说不清的，写「需人工确认」。分层是为了不浪费——让模型逐行看代码，是最贵也最不稳的做法。

**原则三：承诺要能兑现，兑现不了的写进「已知限制」。**
`docs/limits.md` 是对外承诺：那里写着抓不到的，就是真的抓不到。这份文件比功能列表重要，
因为读它的人能据此决定「哪些我得自己看」。

## 5. 四层判定：为什么不是一个 linter

很多工具号称「代码规范检查」，实际上只做第一层。stdkit 把判定拆成四层，是因为这四层的**判据位置**完全不同。

| 层 | 判据在哪 | 谁来做 | 命令 | 输出形态 |
|---|---|---|---|---|
| 行级 | 一行文本长什么样 | 本机正则 | `ds scan` | `文件:行号` + 规则 ID |
| 仓级 | 文件集合（目录、文件名） | 本机比对文件名 | `ds cross` | `文件` + 规则 ID |
| 语义 | 调用链、数据关系、跨文件语义 | 模型（或人） | `ds brief` 给出清单 | 自然语言结论 |
| 人工 | 规范说不清的取舍 | 人 | — | 「需人工确认」 |

举几个具体例子，你会立刻明白为什么这么分：

- `private double amount;` —— 一行就能判，命中 `J8-API-04`。行级。
- `catch (Exception e) { }` 写在两行里 —— 单行正则抓不到，这是行级的已知短板，写进了 `limits.md`。
- `sql/upgrade/mysql/002_b.sql` 有没有同名回滚 —— 判据是「另一个文件存不存在」，跟这一行的内容无关。仓级。
- 「这个事务边界对不对」「这条写路径幂等不幂等」 —— 要看调用链和数据库约束。语义。
- 「这个字段名算不算业务黑话」 —— 团队自己都说不清，归人工。

**为什么行级和仓级要用两个命令？** 因为输出语义不一样。行级检查的输出带行号，这样 `--diff`（只看本次改动）
和 baseline（按「规则+文件+行」豁免存量）才成立。仓级问题的答案不是「哪一行」，而是「哪个文件」。
把两者混进一个命令，diff 与豁免的行级语义就会被破坏。所以 `ds cross` 是独立命令，它也复用同一套规则 ID。

## 6. 一条规则长什么样

规则就是 Markdown。解析器只认一个约定：`###` 标题以 `域-分类-序号` 开头，紧跟一个 ` ```txt rule ` 元数据块。

````markdown
### J8-API-02 金额必须用 BigDecimal

```txt rule
level: must
severity: critical
tags: money, precision
applies: **/*.java
p3c: OOP 规约 10
deny: \b(?:double|float)\s+\w*(?:amount|price|fee|balance)\w*\b
```

**规则**：金额、费率、税额、余额禁止 `double` / `float`，含 DTO、PO、中间变量。

**为什么**：二进制浮点无法精确表示 `0.1`，累加后必然对不上账。

```java
// BAD
private double amount;
```
````

元数据块里的键，各有各的用处。挑几个不容易一眼看懂的说明：

| 键 | 干什么 | 为什么需要它 |
|---|---|---|
| `applies` | 这条规则管哪些文件（glob） | 同一条规则在不同目录下意义不同 |
| `exclude` | 整文件例外 | 条文里写「布局壳可以不 scoped」，就必须有机制接住，否则规则会在自己的正例上开火 |
| `raw` | 匹配前**不**剥离注释 | 有些规则专门看注释（比如 TODO 必须带工单号） |
| `noString` | 先抹掉字符串内容再匹配 | `var` / `record` 这类关键字判断，会把示例文本误判成代码 |
| `deny` / `allow` | 命中即违规 / 命中则豁免 | 确定性层的全部内容 |
| `maxHits` | 同一文件命中超过 N 处才算违规 | 有些规范的判据是「次数」而不是「形态」，见下 |
| `status` | `active` / `retired` | 删规则不删 ID：老引用还能查得到，只是不再参与扫描 |

**示例块不是装饰，它会被反向校验。** `ds check` 要求每条 `deny` 至少命中本规则 `// BAD` 里的一行，
而且**不许**命中 `// GOOD` 里的行。这条约束挡掉的是最常见的一类坏规则：凭想象写了个正则，
从没在真实代码上跑过，写完之后要么永不命中，要么到处误报。

### `maxHits`：判据是次数的那种规则

「一个页面里出现 5 个以上原始请求，就该抽到 `src/api/`」——这条规范没法写成单行的「禁止什么」，
因为 4 处是允许的、5 处才违规。于是加了 `maxHits`：

```txt rule
applies: **/views/**/*.vue
deny: \b(?:request|http|api|axios)\.(?:get|post|put|patch|delete)\s*\(
maxHits: 4
```

含义：允许 4 处，第 5 处报一次。只报越线那一处，不是把第 5、6、7 处全报一遍——一条已经说明问题，
重复刷没有信息量。

这里有个坑值得写下来：`--diff` 模式下，**计数必须在 diff 过滤之前做**。如果先按改动行过滤，
「文件里已经有 4 处、这次新增 1 处」就只会被计数成 1 处，永远不报。这个 bug 在 0.19.x 真实发生过，
修完之后把语义定死为：**计数按整文件，只有越线那一行落在本次改动内才报**。这条规则现在有对应的单测守着。

## 7. 生成链：规则怎么变成 AI 能用的东西

`ds build` 会把 `rules/` + `policy/` 生成为四类产物：

| 产物 | 给谁用 | 内容 |
|---|---|---|
| `dist/skills/write-java/` 等 4 个 | 写代码时 | `SKILL.md`（怎么用、边界）+ `references/`（规则全文） |
| `dist/prompts/review-java.md` 等 4 个 | 审查时 | A 类机械命中清单 + 仓级命令 + B 类待判清单 + 结论模板 |
| `dist/adapters/{claude,codex,cursor,copilot}/` | 各客户端 | 各自的入口文件、命令定义、`AGENTS.md` |
| `dist/AGENTS.md` | 任意支持 AGENTS.md 的工具 | 仓级约定 + 已知限制 |

为什么要有 `catalog/rules.json` 这一层中间产物？两个原因。

第一，**解析一次，多处使用**。Markdown 解析（尤其是元数据块、示例分段）有成本也有歧义，做成结构化索引后，
`scan`、`brief`、`build`、扩展都读同一份，不会出现「A 处解析成 3 条规则、B 处解析成 4 条」。

第二，**索引可校验**。索引是确定性生成物（不含时间戳），可以直接与规则正文比对：
规则改了但没重建索引，`ds check` 立刻报错。这就是「产物不许手改」的落地方式。

**为什么 `dist/` 要提交进 git？** 因为客户端（比如 pi、Claude Code）需要的是一个可以直接安装的目录。
如果每次都要用户先 `git clone` 再 `ds build`，安装门槛就变成了两步以上。`dist/` 自带 `cli/`、`catalog/`、
`LICENSE`，装到任何地方都能独立运行——包括装进一个没有 `rules/` 的目录，这时 `ds check` 会明确说
「这是 dist 安装，自检跳过」，而不是喷几百条假错误。

## 8. 确定性引擎：一次 `ds scan` 到底做了什么

入口是 `cli/lib/scan.mjs`。按执行顺序讲，每一步都有它必须存在的理由。

**第一步，枚举文件。**
在 git 仓库里用 `git ls-files`（含未跟踪但未被忽略的文件），这样 `.gitignore` 自动生效，
构建产物与 `node_modules` 不会进来。非 git 目录退回遍历，只跳机器产物目录。
这中间踩过一个坑：`execFileSync` 默认把子进程的 stderr **透传**出来，于是扫一个非 git 目录会往 stderr 打一行
`fatal: not a git repository`。人看着是噪音，但如果调用方把 stdout 和 stderr 一起读进缓冲区（我们的测试就是），
`--json` 的输出就被这行污染了。现在两处 git 调用都显式 `stdio: [ignore, pipe, pipe]`，并把 git 自己的话拼进报错。

**第二步，剥离注释。**
注释里经常有示例代码（`// 不要这样写：private double amount;`）。不剥的话，规则会在教人别犯错的注释上开火。
剥离是按文件类型走不同状态机的：

- `.java` / `.js` 走 C 系（`//`、`/* */`）；
- `.sql` 只认 `--`；
- `.vue` **按块**处理：`<template>` 里是 HTML 注释，`<script>` 里是 C 系，`<style>` 里只有 CSS 块注释；
- XML/HTML 跳过引号内的内容与 CDATA —— 否则 `<!--` 出现在字符串里时，会把文件后半段整段当注释剥掉，
  于是「后半段对全部规则静默失效」。这种失效比误报危险得多，因为它看起来是绿的。

字符串内容默认**保留**，因为很多规则要看字符串里的 SQL。需要避开字符串的规则（`var`、`record` 这类关键字）
显式写 `noString: true`。

**第三步，逐行匹配。**
对每一行，先看文件路径是否匹配规则的 `applies`、是否在 `exclude` 里；再跑 `allow`（命中就跳过）；再跑 `deny`。
命中就产出一条记录：规则 ID、生效级别、文件、行号、掩码后的片段。

**第四步，掩码。**
命中片段默认把值替换成 `***`。原因是：`J8-SPR-15` 抓的就是明文口令，如果输出把
`spring.datasource.password=root123` 原样打出来，这条规则本身就变成了泄漏源——它会进 CI 日志、
进模型上下文、进别人屏幕。想看原文用 `--no-mask`，本地排障时用。

**第五步，收口与排序。**
`maxHits` 在这里生效（超额只留越线一处）；diff 模式在这里按改动行过滤；最后按文件、行号、级别排序。

**性能这件事也被检查。** 正则有几种写法会指数级回溯（`(x+)+` 这种嵌套量词，在超长单行上能跑几十秒）。
所以有两条守卫：`ds check` 编译规则时，把 `deny`/`allow` 跑一遍 2 万字符的探测串，超过 100ms 就警告；
另外检测嵌套量词，直接提示改写法。还有一个固定种子的模糊测试：400 组随机片段拼出来的文件，
必须不挂死、不抛错、每例 2 秒内跑完。200ms 曾把 CI 打成红灯（2 核 runner 并发跑三个测试文件时会抖），
放宽到 2 秒——它要抓的是死循环，不是性能基准。

## 9. 仓级判定：`ds cross`

只有两条规则，都是「判据在文件集合里」的那种：

| 规则 | 判据 | 为什么重要 |
|---|---|---|
| `SQL-RBK-01` | 每个 `sql/upgrade/<方言>/00N_x.sql` 必须有同名回滚脚本 | 上线出问题要回滚，回滚脚本没有就是事故 |
| `SQL-DIA-01` | L3（`AGENTS.md`）声明的引擎方言目录都存在，且各目录脚本序号集合一致 | 只给 MySQL 写了脚本、PostgreSQL 漏了，是先上线后发现的典型 |

两条的共同点：**不需要读脚本内容，只看文件名和目录结构**。这就是它能做到零误报的原因。
非标准布局（没有 `sql/upgrade/<方言>/` 结构的仓）直接跳过，不误报也不报——那种仓的目录约定需要人确认。

它也是唯一会读业务仓 `AGENTS.md` 的地方，而且**只读 `engines` 一格**。这个边界写在 `limits.md` 里：
`ds cross` 不是「读你的仓然后猜」，只有明确声明的那一格参与判定。

## 10. 策略、豁免，以及「降级」和「豁免」的区别

严重级不是写死在规则里的。三层覆盖，后者盖前者：

```
policy/default.json            ← 默认：critical + high 阻断
policy/profiles/<name>.json    ← --profile 指定（当前有 jdk8-vue2）
<业务仓>/.stdkit/policy.json    ← 单仓覆盖，优先级最高
```

合并方式是**浅合并**：后一层整体替换同名键，不做递归合并。这条要记牢——如果你在 profile 里写了
`stack`，业务仓再写一个 `stack`，整体就被换掉了，不是取并集。

三层各有**键白名单**，写错键名直接报错。这个设计来自实际教训：配置项拼错（`blockon` 而不是 `blockOn`）
如果静默忽略，表现就是「我明明配了，怎么没生效」，排查半小时起步。同类坑这个项目踩过不止一次
（`status: retird`、`raw: yes`、`historyAllow` 里的 id 拼错），所以统一改成「不认识就喊」。

**两个容易混的概念：**

- **降级**（`.stdkit/policy.json` 的 `severity`）：这条规则在本仓就该是 `medium`。长期决策，没有到期日。
- **豁免**（`.stdkit/baseline.json` 的 `waivers`）：历史代码这次不动。**必须写 `until`**，到期自动失效并重新计入。

为什么非要两套？因为它们的动机不同。降级是「我们团队的判断和默认不同」，豁免是「这笔债我欠着，但我会还」。
把后者做成永久的，就等于把技术债洗成了制度。

阻断阈值也是常被误解的一处：`--fail-on high` 表示「high **及以上**阻断」，不是「只有 high」。
所以 `policy` 里写 `blockOn: ["low"]` 的结果是**全部阻断**，而不是只阻断 low。
（早先 `ds scan` 用精确集合、`ds brief` 用阈值，两个命令会给出相反结论，这是一个真实的 bug，现在共用一套语义。）

## 11. 写前护栏：在文件落盘前拦一次

`extensions/stdkit.ts` 是 pi 的扩展，监听 `tool_call` 事件：模型要 `write` 或 `edit` 一个文件时，
先把内容交给 `scanText` 判一遍，命中 **critical** 就拦下来，并把「哪条规则、哪一行、怎么改」告诉模型。

三个刻意的限制：

1. **只拦 critical。** high/medium 交给审查。护栏的定位是「防止不可逆的错误直接落地」，
   如果一个工具什么都要拦，人会把它关掉，那它就什么都没拦住。
2. **只拦 `write` / `edit`。** 别的工具（读、跑命令）不管。
3. **`edit` 的行号是块内偏移**，不是文件真实行号。所以护栏提示里的行号只能当参考，这句话写进了 `limits.md`。

护栏的判定不在 `.ts` 里。`extensions/stdkit.ts` 只有 184 行，全是 pi 的胶水（注册工具、路由事件）；
真正的判定在 `cli/lib/guard.mjs`，纯函数，可以单测。为什么这么拆？因为 `.ts` 依赖 typebox 和 pi SDK，
单测跑不起来；判定逻辑搬出来之后，护栏这个「唯一会阻止人落盘」的部件才有测试。

## 12. 发布链路：先把该藏的藏好

这个项目要开源，所以「发布前别把内部东西带出去」必须是命令，不能是记性。

`ds publish-check` 读 `policy/publish.json`，按三类规则扫：

- **凭证形态**：内网 IP、云厂商 key、支付平台密钥、私钥头；
- **内部标识**：内部仓库名、业务字段名、内部账号与域名；
- **环境痕迹**：本机绝对路径（`<盘符>:/work/...`）、内部工作区目录名。

两个设计细节值得说：

**一，扫描集合必须来自 git。**
一开始用的是目录遍历，结果扫到了 `.idea/workspace.xml`——里面正好有本机绝对路径与工作区名。
问题在于，本机 git 不在 PATH 时，代码会静默退回目录遍历：扫描集合既变大（把 IDE 的本地产物扫进来），
又变小（漏掉只有 git 才认的忽略规则）。现在反过来：**是 git 仓却调不到 git，直接报错并提示设 `DS_GIT`**。
静默降级比报错危险得多。

**二，工作树干净 ≠ 历史干净。**
`git push --force` 只改引用，不删对象。所以有 `--history` 模式：扫可达历史里 diff 的**新增行**
（删掉的行不算，因为现在已经没有了）。历史里的命中改不掉，于是「已知且接受」的逐条写进
`policy/publish.json` 的 `historyAllow`，每条必须带 `reason`，`path` 必须真的能匹配到仓里的文件
（拼错的 glob 照样能编译，配不到才是真信号），理由少于 8 个字会被拒绝——
「历史原因」这种话不是理由。

## 13. 质量保障：六层，各自防不同的错

这个项目的测试不是为了覆盖率，每一层都在防一类具体的错。

| 层 | 命令 | 防什么 | 规模 |
|---|---|---|---|
| 规则仓自检 | `ds check` | 规则本身不合法、产物与规则不同步、文档与实现不一致 | 覆盖 6 大类断言 |
| 确定性层回归 | `ds eval` | 规则写错了也能全绿（漏报/误报） | 23 个用例，49/49 规则有命中断言 |
| 语义层回归 | `ds eval --semantic` | 改 prompt 之后模型的判定悄悄变了 | 2 个用例，记录式比对 |
| 单测 | `npm test` | 纯函数与 CLI 行为回归 | 60 条，4 个文件 |
| 契约冻结 | 同上（`compat.test.mjs`） | 公开契约被无意改掉 | 形状快照 + 退出码实测 |
| 发布脱敏 | `ds publish-check [--history]` | 带内部信息上线 | 11 条 pattern |

**`ds check` 值得单独讲**，因为它是这个项目「自我约束」的主要工具。它检查的东西包括：

- 规则 ID 唯一、前缀与目录一致、元数据键合法、级别取值合法；
- 每条 `deny` 能编译、能命中自己的 `// BAD`、不误命中 `// GOOD`（除非被同规则 `allow` 豁免）；
- `applies` 声明的每种文件格式都有对应的 BAD 样例（防「applies 写了 `.yml`，正则只认 Java 字面量」）；
- 示例代码不用 JDK 9+ 语法（这个仓自己的规则就是 JDK 8）；
- 正文有「规则」与「为什么」、无占位符；条文里写了「例外/豁免」就必须有 `exclude` 或 `allow` 接住；
- `catalog/` 与 `dist/` 与 `rules/` 同步；prompt 里的 A/B 清单等于该域规则全集；
- 文档里提到的命令、参数、规则 ID 都存在；README 里的数字与实际一致；
- 仓根只放白名单文件（防止临时脚本混进来）。

**「注入验证」是这个项目的一个习惯。** 写完一条断言，故意把被保护的东西改坏，确认它真的会红，
再改回来。比如加了 `historyAllow` 的四条断言后，分别注入坏 id、坏 path、短 reason、全域放行，
四条各红一次；加了 `compat` 形状快照后，删掉 catalog 的一个必需键、加一个未登记字段、改掉退出码语义，
三次都红且报错里带升级步骤。断言没被验证过，就等于没有。

## 14. 关键取舍（以及被否掉的方案）

这一节大概是这份文档最有价值的部分：每个决定都写清「否则会怎样」。

| 决定 | 备选方案 | 为什么选现在这个 |
|---|---|---|
| 规则用 Markdown + 元数据块 | YAML / JSON 配置 | 规则主要给人读，正文里要放反例代码；YAML 里塞代码块很丑 |
| 不做 AST，只做单行正则 | 上 ESLint/PMD 这类真正的语法分析 | AST 要装依赖、要维护解析器版本；正则覆盖了「形态类」问题的绝大多数，代价是抓不到跨行结构（已写进限制） |
| 单栈（JDK 8 + Vue 2） | 同时支持 JDK 17 / Vue 3 / TS | 同一条规则在不同栈下正反颠倒，规则文件必须按版本分叉，`deny` 会变成依赖 profile 的分支。ADR 0002 明确不做 |
| 语义层回归不调模型 | `ds eval --semantic` 直接调 LLM | 调了就要 API key 和网络，CI 会 flaky，也破坏「clone 下来就能用」。改成「记录 + 比对」：工具只比静态记录，模型由人手动跑 |
| 仓级检查独立成 `ds cross` | 塞进 `ds scan` | 会破坏 `--diff` 与 baseline 的行级语义（仓级问题没有行号） |
| 不提供 demo 业务仓 | 造一个示例项目 | demo 要演示命中就必须含违规代码，会被照抄；两份仓必然漂移，而漂移的 demo 比没有更误导 |
| 不提供 `policy.disable` 关规则 | 允许彻底关掉某条规则 | 关掉之后「为什么没报」会变成考古题。只用 `severity` 降级（长期）和 baseline（短期带到期日） |
| 豁免用文件级而非行级 | 按行豁免 | 行号会漂（改一行代码，下面的全部偏移），维护成本高且容易失效 |
| 1.0 只冻形状不冻内容 | 连规则集合一起冻 | 冻内容意味着不能增删规则；冻形状只约束「键与类型」，规则仍可演进（如 `maxHits` 就是后来加的可选字段） |

## 16. 已知局限

诚实部分，完整清单在 [docs/limits.md](limits.md)。这里只说最需要知道的四条：

1. **49/127 能自动判**，剩下的靠模型读条文。没报不等于没问题。
2. **单栈**。JDK 17 / Vue 3 / TypeScript 没有规则域，硬接会看到成片误报。
3. **正则只看单行**。跨行空 `catch`、跨行的 `@Select(` 拼接、`.yml` 块标量都抓不到。
4. **`ds cross` 只认标准布局**。不是 `sql/upgrade/<方言>/` 结构的仓会直接跳过。
