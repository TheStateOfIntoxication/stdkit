# 0005 多版本规则：把「版本」变成规则属性而不是目录名

## 状态

提议（未实施）。0.20.0 已完成 P0 的一部分（把版本门禁的数据准备好），P1 待定。

## 背景与问题

现在这套规则只覆盖 **JDK 8 + Vue 2.7**，而「8」在三处被焊死：

| 位置 | 形态 | 说明 |
|---|---|---|
| 目录 | `rules/java-jdk8/` | 域的名字里带版本 |
| 规则 ID | `J8-API-04` 等 71 条 | 前缀 `J8` 与 `DOMAINS` 映射一一对应，`ds check` 会断言「ID 前缀必须与目录一致」 |
| 版本门禁 | `policy/jdk8-api.json` 的 25 条 | 每条只有 `pattern` / `hint`，没有「从哪个版本开始可用」；规则 `J8-MOD-01` 的 `deny` 就是把这 25 条拼起来 |

如果照现在的方式加 JDK 17，只有一种做法：新建 `rules/java-jdk17/`、新前缀 `J17`、把 71 条规则复制一份。
这条路能跑，但会立刻违背这个项目存在的理由——**同一件事有三份副本，靠人保持一致**。

不过先看清楚一件事：**真正随版本变化的规则只有 3 条**。

对 71 条 J8 规则做了一遍正文扫描（找「JDK 8」「J8」「isBlank」「record」「var」这类词），结果是：

- `J8-MOD-01`（JDK9+ API 与语法禁止进入 J8 代码）—— 版本门禁本身，随版本变；
- `J8-API-03`（字符串判空统一走 `StringUtils`）—— 正文里写着「JDK 8 没有 `String#isBlank`」，17 下这句话不成立；
- `J8-EXC-02`（可关闭资源用 try-with-resources）—— 正文提到「JDK 8 没有 `InputStream#transferTo`」。

其余 68 条（金额用 `BigDecimal`、SQL 注入、事务边界、命名、幂等、日志、MyBatis 用法…）**跨版本都成立**，
在 17 下不会因为版本而改变结论。

所以问题的形状是：**68 条通用规则被放进了「版本命名」的目录里，导致无法复用；3 条版本相关规则没有地方表达「适用哪一版」。**

## 决策

**把版本从「目录名」变成「规则属性」，域回归技术维度（`java`），版本由业务仓声明、由规则约束。**

具体设计（P1）：

1. **域与 ID**
   - 域从 `java-jdk8` 改为 `java`；`DOMAINS` 的映射放宽成「一个域可以有多组历史前缀」，
     已发布的 `J8-` 前缀**不改号**（`AGENTS.md` 明确「一经发布不改号」），
     在 `docs/concepts.md` 写清：**`J8-` 是历史前缀，表示「源自 JDK 8 时期的规则」，不代表只适用 8**。
   - 新增规则用新前缀 `JAVA-`（或继续用 `J8-`）。这条两选一，倾向后者——前缀换来换去只会让人更困惑。

2. **规则声明适用范围**（元数据，可选，缺省 = 全版本）
   ```txt rule
   until: 8      # 只适用于 <= 8（例如「不要用 String#isBlank」）
   since: 9      # 只适用于 >= 9（例如「用 text block 替代长字符串拼接」）
   ```
   不用区间语法（`>=11 <17`）。现实中绝大多数规则要么是「老版本特化」、要么是「新版本才有」，
   两个单向字段够用，也容易校验。

3. **业务仓声明版本**（L3 `AGENTS.md`）
   `Java: 17` 这一格已经存在：`ds init` 会从 `pom.xml` 的 `<java.version>` / `maven.compiler.source` /
   Gradle 的 `sourceCompatibility` 探测，`ds doctor` 会比对 L3 与实际是否一致。多版本只需要**用它**。
   **未声明时的默认行为**：不做任何过滤，并把「未声明 Java 版本」作为一条 WARN 打出来
   （既不能默认 8——17 的仓会被误报一片；也不能默认最新——8 的仓会被放过）。

4. **门禁数据升级**：`policy/jdk8-api.json` → `policy/jdk-api.json`，每条加 `since`：
   ```jsonc
   { "id": "record", "pattern": "\\brecord\\s+[A-Z]\\w*\\s*\\(", "since": 16, "hint": "record 是 Java 16+" }
   ```
   规则 `J8-MOD-01` 从「固定 deny 列表」变成「按声明版本动态判定」：
   对 `Java: 17` 的仓，只拦 `since > 17` 的构造（`sealed` 是 17、text block 15、`var` 10 都放行）。
   这是多版本里**收益最大**的一块——同一个门禁，对 8 严格、对 17 就只剩 4 条。

5. **eval 支持版本矩阵**
   用例的 `expect.json` 加可选 `javaVersion`；覆盖率断言从「每条规则命中一次」变成
   「每条规则在它适用的版本下命中一次」。否则 `since: 9` 的规则永远不会有命中断言。

6. **prompt 不按版本分叉**
   `dist/skills/*` 与 `dist/prompts/*` 仍然各只有一份，版本标注写在规则那一行（`（jdk>=9）`）。
   生成 3 套 skill 的维护成本会立刻翻三倍，而模型读得懂「这条只适用于 jdk>=9」。

## 备选与为什么不选

| 方案 | 做法 | 为什么不选 |
|---|---|---|
| A. 每版本一个域 | 新建 `rules/java-jdk17/`，复制 71 条 | 半年内必然漂移；改一条通用规则要改 N 处，正是这个项目要消灭的问题 |
| A'. 只把差异放新域 | 共用规则留在 `java-jdk8`，新域只放 17 专属 | 域名有误导性（`java-jdk8` 里躺着通用规则）；ID 前缀 `J8-` 也会让人以为不适用于 17 |
| C. 不改结构，只加文档说明 | 在 skill 里写「JDK 17 下这些规则不适用」 | 判定仍然会误报（`J8-MOD-01` 在 17 仓里照样拦 `var`），文档解释不了绿色的假象 |
| D. 上真正的语法分析（AST） | 用 javac / PMD 的 API 判断语法树 | 引入依赖与 JDK 版本绑定；本项目的差异化价值不在「更准的语法分析」，而在「一份规则、多层判定、产物生成」 |

## 后果

**好处**

- 通用规则写一次，8/11/17/21 共用；版本差异收敛到「3 条规则 + 1 份门禁数据」；
- 版本门禁变成数据驱动，加 JDK 21 只需给清单加条目（`since: 21`），不用写新规则；
- Vue 3 的扩展复用同一套机制（`V2-BASE-01` 禁 `<script setup>` 在 Vue 3 下结论相反，正好是 `until` 的用例）。

**代价与风险**

- 这是一次**结构迁移**：域改名会改变 `catalog` 的 `domain` 值，属于对已冻结契约的破坏性变更
  （ADR 0004）。所以要么在 1.0 之前做，要么在 1.0 之后按大版本流程做；
- `ds check` 有几处假设要同步改：`DOMAINS` 单前缀断言、示例守卫 `J8_GUARD`（现在假设「示例必须是 JDK 8 可编译」，
  多版本后应改成「符合该规则声明的版本下限」）、契约快照 `policy/compat.json`；
- `eval` 的覆盖率断言要变成矩阵，用例数量会上升（3 条版本相关规则 × 3 个版本 ≈ 新增 6–8 个用例）；
- 未声明版本时的默认行为必须明确，否则「默认 8」会让 17 的仓误报一片，「默认最新」会放过 8 的仓。

**工时估算**

| 阶段 | 内容 | 估算 |
|---|---|---|
| P0 | `jdk8-api.json` 每条加 `since`；`catalog` 加可选 `rules[].since/until`；`init`/`doctor` 用探测到的版本给提示（**不改变任何现有判定**） | 0.5 人日 |
| P1 | 域改名 + 前缀兼容、`scan` 按版本过滤、门禁动态化、`check` 三处假设同步、`compat.json` 更新 | 2–3 人日 |
| P2 | `eval` 版本矩阵 + 版本相关规则的 `until`/`since` 标注 + 用例补充 | 1 人日 |
| P3 | Vue 3 复用同一机制（`until: 2` / `since: 3`） | 1 人日 |

**触发条件**

1. 出现第二个 JDK 版本真实的接入需求（不是「预计会」）；
2. 或者：有人在 JDK 17 的仓上跑 `ds scan`，被 `J8-MOD-01` 拦下一片 `var` / `record`——那时 P0 的收益立刻兑现。

**现在就能做的最小准备（P0 的第一项）**

给 `policy/jdk8-api.json` 的 25 条各加一个 `since` 字段。这不会改变任何判定结果
（`J8-MOD-01` 仍然只看「有没有命中」），但把「哪个构造从哪个版本开始可用」这件事变成数据，
P1 的门禁动态化只需要读这一个字段。
