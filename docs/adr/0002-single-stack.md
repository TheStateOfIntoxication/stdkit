# 0002 不做 Vue 3 / TypeScript / JDK 17 规则域

## 状态

已采纳（明确不做，不是「暂不支持」）。

## 背景与问题

常见的做法是写一份「全栈通吃」的规范（Vue 3 近千行 + JDK 9+ 语法通道）。本仓若跟着做，会出现三个问题：

1. **同一条规则在不同栈下正反之**：`<script setup>` 在 Vue 3 是推荐写法，在 Vue 2.7 是禁止项；
   `record` 在 JDK 17 正常，在 JDK 8 是 critical。规则文件必须按版本分叉。
2. **`deny` 的适用范围变得可配置**：同一行代码是否违规取决于 profile，规则正文里要写
   「在 jdk17 profile 下不适用」——而模型读到的是同一份条文。
3. **卖点被稀释**：本仓的差异化价值是「老栈 + 团队约定 + 确定性层」，多栈之后它变成「又一个通用 linter」，
   而这个生态里已经有满地的 ESLint / vue-tsc / Checkstyle。

## 决策

**不做** Vue 3、TypeScript、JDK 9+ 的规则域，也不做 `jdk17` profile。理由按权重排：

1. **语义冲突不可解**：把两套互斥的判断塞进一份条文，等于让 `deny` 依赖 profile 分支，
   而这正是我们在 `J8-MOD-01` / `V2-BASE-01` 里最想避免的「同一行代码两种结论」。
2. **边际收益低**：Vue 3 / TS 有 `vue-tsc` + ESLint + Prettier + `tsc --noEmit`，
   这些工具覆盖了绝大部分「可机判」项，而且是语言服务级别的；重做一个子集没有意义。
3. **成本高于计划估计**：加一个域实际要动 **5 处**（`rules/`、`DOMAINS`、`SKILLS`、`REVIEWS` + `scopes`、
   `SKILL_OF_DOMAIN`，见 README「参与维护」），外加每条规则的版本分叉。

## 备选与为什么不选

1. **只加 `jdk17` profile（不改规则，只让 `J8-MOD-01` 在该 profile 下禁用）** —— 成本确实小，
   但等于「用 profile 关掉一条 critical 规则」，其它 J8 规则仍是 JDK 8 语义，用户会以为整个规则集
   适配了 17。**误导比不支持更糟。**
2. **Vue 3 只加「不建议用」的提示型规则** —— 提示型规则不进 `blockOn`，实际价值接近零，
   却要维护两套 `applies` 与示例。
3. **等有第二个真实仓需要再评估** —— 这其实是当前策略：不做，但把这个判断和理由公开写在
   `docs/limits.md` 与这里，比含糊说「暂不支持」更能体现边界。

## 后果

**好处**

- 规则集保持「单栈可判」：48 条 `deny` 全部无版本分支，`severity` 不依赖 profile；
- `J8-MOD-01` / `V2-BASE-01` 这两条「版本门禁」可以保持 `critical` 而不误伤；
- 文档可以诚实地写「不支持，因为 X」，用户不会踩坑才发现。

**代价**

- 用 JDK 17 或 Vue 3 的仓不能直接用本仓（需改造或放弃）；
- 若未来团队整体迁到新栈，本仓需要重写而不是增量扩展。

**触发复盘的条件**

1. 团队主力仓迁移到 JDK 17+ 或 Vue 3（此时应新建 `rules/jdk17/` 独立域，而不是在 `java-jdk8` 里分叉）；
2. 出现「同一份代码在两种栈下都要审」的真实需求（如长期双栈过渡期）。

如果真要做，正确形态是**新域**而不是 profile：`rules/jdk17/` + 独立的 `J17-*` 前缀，
让两套规则在同一份 catalog 里各管各的，而不是让一条规则按 profile 变形。
