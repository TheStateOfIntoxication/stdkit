# 规则来源与原创性

这份文件回答一个问题：**这些规则是从哪来的，哪些是原创的？**

## 三条来源

| 来源 | 说明 | 占比（约） |
|---|---|---|
| 《阿里巴巴 Java 开发手册》 | 条文形态与分类体系参考该手册；每条规则元数据里的 `p3c:` 字段标出对应条款（`-` 表示无对应条款） | 结构参考 + 部分条款 |
| 团队实践 | 从真实项目里踩出来的坑，写成本仓条文（尤其是 `SQL-*`、`V2-*`、`J8-MBT-*` 里的多方言与幂等部分） | 多数 |
| 公开通用常识 | `BigDecimal`、`try-with-resources`、`#{}` 与 `${}` 的区别这类无争议的工程常识 | 少数 |

## 著作权与原创性

- **著作权人**：`TheStateOfIntoxication`（GitHub 账号），与本仓 [LICENSE](../LICENSE) 的署名、`package.json`
  的 `author` 一致——这三处由 `ds check` 断言，改一处漏改另一处会报错。
- **全部条文为本仓原创撰写**：规则的「规则 / 为什么 / 示例 / 元数据」四部分都是本仓写法，
  未从任何其他规范包复制正文。机器判定可用性反过来说明了这一点：每条 `deny` 都要配得上
  `// GOOD` 与 `// BAD` 双侧示例（`ds check` 反向校验），照抄现成规则集填不出这两侧。
- **不继承任何其他包的授权**：本仓不打包、不改写、不分发第三方规范包的条文；因此许可问题
  只有一处——本仓的 MIT。

## 与《阿里巴巴 Java 开发手册》的关系

只做「**命名与结构对齐**」，不做内容搬运：

- 分类段（`NAM` / `SEC` / `MBT` …）沿用手册的命名风格，便于读者建立映射；
- 规则 ID（`J8-API-04`）是本仓自己的稳定标识；
- `p3c:` 字段只标「本规则对应手册哪一条」，用于和 p3c-pmd / IDE 插件的检查结果对账，
  手册条款编号属于手册自身体系，与本仓 MIT 授权无关。

内容层面：本仓**不复刻**手册原文，也不打包手册内容；条文全部按团队实际踩坑重写。

## 规则的形态

每条规则由四部分组成，都是本仓原创的写法：

1. **元数据块**：`level` / `severity` / `applies` / `deny` / `allow` …（见 `docs/rule-format.md`）
2. **规则**：可执行的一句话，写「禁止什么 / 必须什么」
3. **为什么**：失败后的真实后果
4. **示例**：`// GOOD` 与 `// BAD` 围栏，会被 `ds check` 反向校验

`deny` 正则全部为本仓编写，不是从 p3c-pmd 或 ESLint 复制——那两者的规则集与检查时机都不同，
双份维护只会互相冲突（分工见 `docs/static-analysis.md`）。

## 怎么核对

```bash
node cli/ds.mjs rules --tag money        # 按标签看规则
node cli/ds.mjs rules --domain java-jdk8 # 按域看
```

每条规则的 `file:line` 会打印出来，可以顺着读到正文。
